# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

Maven plugin (`org.cyclonedx:cyclonedx-maven-plugin`, packaging `maven-plugin`) that generates CycloneDX SBOMs from a Maven build's dependency graph. It targets Java 8 (`maven.compiler.release=8`) and requires Maven 3.1+ at runtime. Current dev version is `2.9.2-SNAPSHOT`; the 2.9.x line targets CycloneDX schema 1.6.

## Build and test

```bash
# Full CI build: unit tests + Maven invoker integration tests + site
mvn --no-transfer-progress verify site

# Unit/JUnit tests only (skips the invoker-plugin IT suite under src/it)
mvn test

# Run a single test class (Surefire)
mvn test -Dtest=BomDependenciesTest

# Run a single test method
mvn test -Dtest=BomDependenciesTest#testBomDependencies

# Run only the src/it integration tests by name
mvn verify -Dinvoker.test=makeAggregateBom
```

JDK 8 is required — the `release` profile has an enforcer rule pinning Java to 1.8. The GitHub Actions CI (`.github/workflows/maven.yml`) runs on JDK 8, `adopt` distribution.

The `release.sh` script is macOS-only (uses `/usr/libexec/java_home`) and runs `mvn release:prepare release:perform -Prelease` to publish to Maven Central via OSSRH.

## Architecture

Three Mojos extend a common base, all bound to the `package` phase by default:

- `BaseCycloneDxMojo` (`src/main/java/org/cyclonedx/maven/BaseCycloneDxMojo.java`) — holds every `@Parameter` shared by the goals (schema version, output format/name/dir, scope include flags, `skip*` flags, external references, `outputTimestamp` for reproducibility) and owns SBOM assembly: delegates component/dependency extraction to `ModelConverter` + `ProjectDependenciesConverter`, then writes JSON/XML via `cyclonedx-core-java`'s `BomGeneratorFactory` and re-parses the output to validate it. BOMs are attached to the Maven project as secondary artifacts under classifier `cyclonedx` (property `cyclonedx.classifier`).
- `CycloneDxMojo` (`makeBom`) — per-module BOM. Resolves a `ProjectDependencyAnalyzer` via Plexus (`projectDependencyAnalyzerName`, default `default`) to classify used/unused/declared deps.
- `CycloneDxAggregateMojo` (`makeAggregateBom`) — extends `CycloneDxMojo`, marked `aggregator = true`, walks `reactorProjects` and produces a root aggregate BOM plus per-module BOMs (gated by `outputReactorProjects`). Implements the `excludeArtifactId` / `excludeGroupId` / `excludeTestProject` filters from the README.
- `CycloneDxPackageMojo` (`makePackageBom`) — restricted to `war`/`ear` packaging.

Supporting pieces:

- `DefaultModelConverter` / `ModelConverter` — turns a Maven `Artifact` into a CycloneDX `Component` (pURL, hashes, licenses, externalReferences from the POM).
- `DefaultProjectDependenciesConverter` / `ProjectDependenciesConverter` — walks the dependency graph (via `maven-dependency-tree`) and produces the `BomDependencies` record used by every Mojo. Scope filtering lives here.
- `DelegatingRepositorySystem` — wraps Aether `RepositorySystem` so resolution picks up test-only overrides.
- `ExtendedMojoConfigurator` + `ExternalReferenceTypeConverter` — a custom Plexus component configurator (role-hint `cyclonedx-mojo-component-configurator`, referenced from each `@Mojo(configurator=...)`) that registers a converter so `<externalReferences><externalReference><type>…</type></externalReference></externalReferences>` in plugin configuration deserializes to the CycloneDX enum. The sisu-maven-plugin's `main-index` goal (in the POM build section) is what makes this named component discoverable at runtime — don't remove it.

## Tests

Two parallel suites:

1. **JUnit suite** under `src/test/java/org/cyclonedx/maven/` — driven by Takari's `takari-plugin-testing` / `takari-plugin-integration-testing`. `BaseMavenVerifier` boots a `MavenRuntime`, uses `TestResources` to copy a test project from `src/test/resources/<name>/` into `target/test-classes/transformed-projects/`, and runs `clean package` against it. The current plugin version is injected via `-Dcurrent.version=…`, read from `test.properties` generated by `takari-lifecycle-plugin`'s `testProperties` goal. Test POMs reference `${current.version}`, so a clean + full compile (`mvn test-compile`) must run once before individual tests are viable from an IDE. Most tests load the generated XML BOM from `target/bom.xml` and assert against the DOM via helpers in `TestUtils`.
2. **Maven Invoker IT suite** under `src/it/` — driven by `maven-invoker-plugin` during `verify`. Each subdir (`makeAggregateBom`, `makeBom`) is a standalone Maven project with a `verify.groovy` post-build script that asserts on the generated BOM files. IT projects share the settings file `src/it/settings.xml` and use `${project.build.directory}/local-repo` as their local repository.

When adding a regression test for a GitHub issue, the convention is a test class named `Issue<number>Test` with a matching `src/test/resources/issue-<number>/` project tree.

## Release & site

- The `release` Maven profile signs artifacts (`maven-gpg-plugin`), attaches sources/javadocs, and enforces JDK 8.
- `mvn site` builds the Maven plugin documentation (uses `maven-plugin-report-plugin`). The CI job publishes `target/site` to the `gh-pages` branch on push to `master`.
- `src/site/markdown/` holds hand-written doc pages (e.g. `external-references.md`); README.md is copied into the site as `index.md` by the `maven-antrun-plugin` execution bound to `pre-site`.
